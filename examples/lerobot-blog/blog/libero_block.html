Does any of this make a better robot?

Search and mining are only worth doing if the training set they produce trains a better policy. That is hard to measure on DROID, because there is no simulator to run the policy in. So for this one test we moved to LIBERO, a simulation benchmark where a policy is scored on whether it completes the task. Success rate is the metric here, and it is the one that matters.

LIBERO’s dataset is also unusually clean: 1,693 demonstrations of 40 tasks, every one successful, every one with the right instruction attached. Real teleop collections are not like that. So we broke it on purpose. We picked a random 30% of the episodes and gave each third of them one defect that shows up in real collections. The camera frames were never touched. All three defects live in the tabular data, which is also where real logging bugs live.

For each defect there is a column that catches it. Each column is computed from what the table already holds, and an episode is flagged when its value is far outside the normal range for its task:

what we brokehow you can tellthe column
Wrong instruction. The task label is swapped for another task in the same suite. The episode’s last frames look unlike the last frames of other episodes with the same label. goal_dist, per episode
Shaky arm commands. Noise on the arm actions, a spike on 4% of frames, the gripper flipped on 2%. The commanded action jumps around from one frame to the next. jerk_score, per frame
Out of sync. The action stream runs 0.6 seconds ahead of the video, like a timestamp bug. The commanded motion only lines up with the motion the robot actually made after shifting it by several frames. act_lag, per episode

Thresholds are robust z-scores within each task, 3.0 in every case. Nothing in these checks knows which episodes were broken.

An episode that trips any of the three rules gets quality_flag set to the name of the defect. Everything else is ok. The columns are written onto the frames table, and the training set is one filter over them:

three columns, one filter

frames = lancedb.connect(root).open_table("frames")
frames.merge(per_frame,   left_on="index")           # jerk_score
frames.merge(per_episode, left_on="episode_index")   # act_lag, goal_dist, quality_flag

keep = frames.search().where("quality_flag = 'ok'") \
             .select(["episode_index"]).to_arrow()   # 1,199 episodes -> --dataset.episodes

0.2 s to write the columns · table version 1 → 6 · no video touched · the trainer takes the episode list, nothing is copied

merge is a left join on the key column. It adds the new columns and rewrites nothing else, so readers on the old version keep working. The per-episode scores are joined on episode_index, so every frame of an episode carries them. LeRobot’s trainer takes a list of episodes, so the result of the filter becomes --dataset.episodes. If you will reuse a split, the same filter can be saved as a materialized view, a named table that refreshes when the scores change. Here is what the table looks like afterwards:

Then we trained SmolVLA four times with the same recipe, 40,000 steps each, and scored each model in the simulator on 10 rollouts of every task, 400 rollouts per model. The four training sets were:

  • Clean. The original dataset, before we broke anything. This is the best case.
  • Messy. The broken dataset with nothing removed. This is what training on bad data costs.
  • Messy, flagged episodes removed. The broken dataset minus everything the three columns flagged. This is our method.
  • Messy, exactly the broken episodes removed. This row cheats. It uses the list of what we broke, which no real dataset comes with. It shows the best any detector could possibly do, so you can see how close the three columns got.

Success rate in %, 100 rollouts per suite. Same seed, same recipe, same steps for every row.

Breaking 30% of the data cost 23 points, from 86.0 to 62.7. Removing what the three columns flagged brought back 14 of them, to 77.0. Removing exactly the broken episodes would have reached 80.2, so the columns got most of the way to the ceiling. The remaining gap to the clean model is mostly the price of training on 30% fewer episodes, not of bad data left behind.

The biggest recovery is on the goal suite, where several tasks share one scene and differ only in the instruction. A wrong label there is fatal, and removing the flagged episodes took success from 48 back to 85.

How well the flags matched what we actually broke. Precision is the share of flagged episodes that were really broken. Recall is the share of broken episodes that were flagged.

The flags were right 96% of the time and caught 93% of the broken episodes. 20 clean episodes were dropped by mistake, and 33 broken ones stayed in. Almost all of the misses are wrong labels in the spatial suite, where all ten tasks end with the same bowl on the same plate. The last frame cannot tell those labels apart, so neither can a check built on it.

The mess here was injected, and the 10% rates are ours. The three defect types are real ones from teleop collections, and the checks make no use of knowing they were there. On your data the mix will differ, and so will which column does the work. The scripts that broke LIBERO and the ones that found the damage are in the companion repo.
